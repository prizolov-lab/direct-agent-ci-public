# Prizolov Agent Workforce — единый стандарт v2.0
Автор: Dm.Andreyanov
Бренд: Prizolov Lab
Продукт: Prizolov Yandex Direct Agent
Дата: 2026-11-19
Статус: нормативная спецификация; реализация планировщика, очереди и маршрутизации требует отдельной проверки.

## Область действия
Обязателен для каждого действующего и будущего исполнителя, главного исполнителя и независимого проверяющего. Новый исполнитель наследует единый профиль автоматически при регистрации; клиентские настройки не могут ослаблять общие правила безопасности. Отличаются только идентификатор, клиент, задачи, роль и явно разрешённые операции.

## Контракт задачи
Каждая задача содержит task_id, shift_id, agent_id, client_id, assigned_by, assigned_at, deadline_at, priority, scope, required_evidence, approval_requirements, status, updated_at.
Допустимые статусы: queued -> assigned -> acknowledged -> in_progress -> ready_for_review -> verified -> completed. Отдельные: blocked, rejected, cancelled. Смена статуса журналируется, повторная доставка не создаёт второе исполнение (идемпотентность по task_id).
Главный исполнитель распределяет задачи, исполнитель подтверждает получение, выполняет разрешённые действия, сохраняет доказательства и передаёт на независимую проверку. Если исполнитель недоступен, задача остаётся в очереди и эскалируется; получение задания не считается его исполнением.

## Отчётность по Москве (Europe/Moscow)
Каждый исполнитель ежедневно в конце назначенной смены сдаёт отчёт: выполнено, доказательства, результат, незавершённое, блокировки, следующий шаг. Если время конца смены не задано, отчёт формируется к 21:20 МСК как рекомендуемое значение по умолчанию (не ранее фактического завершения смены).
Ежедневно в 21:30 МСК каждый исполнитель сдаёт предложения по улучшению: проблема, подтверждение, решение, эффект, риск, трудоёмкость, приоритет. При отсутствии обоснованных предложений явно сообщает «новых обоснованных предложений нет»; нельзя выдумывать улучшения.
Главный исполнитель агрегирует отчёты и предложения, устраняет дубли, сообщает владельцу общую сводку и просрочки. Неполученные отчёты помечаются missing, а не «успешно выполнено».

## Единый Telegram Gateway
Все роли используют одну очередь уведомлений, один GitHub Worker и один Telegram-бот. Сообщение имеет event_id, agent_id, agent_role, client_id, task_id, shift_id, event_type, created_at, summary, evidence_reference, approval_state. event_type: task_assigned, task_blocked, shift_report, improvement_proposal, review_result, approval_request, system_test.
Секреты Telegram хранятся только в защищённых GitHub Secrets. В публичный репозиторий передаются только минимальные несекретные события; клиентские данные и доказательства остаются в приватном Evidence Store. Фактическая доставка подтверждается квитанцией с Telegram message_id, GitHub run_id и commit SHA. Повторная отправка исключается по event_id. Тесты маркируются system_test и не заявляют о готовности реальных аудитов.

## Безопасность и контроль
Назначение задачи не является согласием на запуск рекламы, изменение бюджета, удаление объектов или другие существенные действия. Проверяются текущие полномочия, кабинет, клиент, объект, актуальное состояние и отдельные подтверждения. При неопределённости — блокировка и эскалация. Независимый проверяющий не подменяет владельца при согласовании расходов.

## Критерии готовности реализации
1. Автоматическое наследование профиля новым агентом.
2. Назначение, получение, обработка и проверка задачи по всей цепочке.
3. Вечерние отчёты всех активных смен; контроль пропусков.
4. Ежедневные предложения в 21:30 МСК, включая отсутствие новых идей.
5. Общий Telegram Gateway с отдельным agent_id и подтверждённым message_id.
6. Тестовые уведомления отделены от реальных.
7. Повторные события не вызывают повторное исполнение или повторную отправку.
8. Ни одна операция с рекламой не обходит согласования.

До подтверждения всех пунктов нельзя заявлять, что автономная система смен и ежедневных отчётов работает в production.
